# 480B through the durable Batch API on the existing four H100s

This follows the [engine qualification](gpu-takeover-2026-10-25.md). The pinned
model is `QuantTrio/Qwen3-Coder-480B-A35B-Instruct-AWQ`, revision
`9ce3eaa67fe88609afec235117e97eb03d9b3cda`: 480B total / approximately 35B
active MoE parameters. No additional cloud resource or paid plan was created.
The current GPU invoice is unknown; measured monetary cost remains `null`.

## Execution and acceptance boundary

The finite canary uses the existing Azure PostgreSQL database and existing S3
HTTPS endpoint. It sends ordinary authenticated `POST /v1/files` and
`POST /v1/batches`, polls the Batch API, and downloads and validates real result
files. Its model-specific worker invokes the real TP4 vLLM engine. This is not
the fixture inference adapter or a direct-engine benchmark.

The experimental canary API/worker ports were private 18148/9118; the engine port
is 8348. The primary API/gateway remained present, while their 235B worker/engine
were stopped during each GPU experiment. Success and failure entered a bounded restoration
of the original serving pair and watchdog. An experimental canary is distinct
from promoting 480B into the primary serving catalog. That promotion and its
separate real primary-API validation have now completed, as recorded below.

Every completed cohort must satisfy all of these invariants:

- Exactly one accepted completed attempt for each completed task.
- Identical accepted token totals in batches, tasks and attempts.
- All requested custom IDs occur exactly once in the downloaded results.
- Actual prompt/output counts equal the preregistered token-cell workload.
- Queue, accepted-attempt and durable completion timestamps come from Azure.

Inputs use the existing pinned public SQuAD text, fitted to 128/512/2,048/8,192/
16,384 tokens, crossed with output caps of 32/128/512/2,048. `min_tokens` fixes
the generated work for capacity comparison. These experiments do not grade
answer quality. Twenty tasks mean 109,056 input and 13,600 output tokens.

## Storage and durability

The primary API uploaded a 260-byte fixture to the existing S3 backend and
read back the identical SHA-256
`6457519d053fb91aca9701fb167b5660179921fea372d329c65786b6875f7738`.
The experiment subsequently requires all its inputs to be external ready S3
objects, explicitly archives its own completed outputs with immutable hashes,
restarts its API and verifies every input/output file digest again. The experiment
itself requested archive-only qualification. The original report incorrectly
asserted `database_payloads_retained: true` without observing other APIs'
background publishers. A subsequent read-only Azure audit found that the existing
primary publishers had already moved all 200 fixture responses/bodies to their
ten ready S3 archives; task identities and usage remain in Azure. The
[correction](platform480-2026-10-25/pilot-v1/storage-audit-correction.json) binds
the original report by SHA-256 and records actual counts. The original report
was not rewritten. Future reports query retained payload counts directly.
The 20 input/output SHA-256 readbacks passed after the canary API restart.

`/workspace` still fails with ENOMEM and remains excluded from mutable runtime
state. This addresses the application path through direct object storage; it
does not claim to repair the provider's FUSE mount. Logs, model staging and
journals use the existing container disk, which is not whole-Pod-loss durable.
The 252 GB checkpoint has pinned public source hashes but no newly uploaded
off-Pod checkpoint copy. Closed evidence is exported to the Mac and private Git
with a size-bounded allowlist and verified transfer hashes.

## Completed three-block KV study

The qualified engine has 172,912 physical KV tokens and 32 maximum sequences.
Eight block-rounded full contexts reserve 147,584 tokens. Sixteen full contexts
do not safely fit. The new operator-only adaptive mode obtains exact prompt
tokens from this exact model's vLLM tokenizer and reserves prompt plus maximum
output in 16-token blocks. Its 164,256-token budget preserves a 5% physical
margin. HTTP/model/usage uncertainty latches admissions closed; engine health
alone cannot reset that latch. Waiting claimed tasks retain lease heartbeats.

The first successor verified pilot restoration, all managed identities,
a drained global queue and exact worker-source hashes before deploying two
compatible worker modules. Its trial refused to proceed: configuration names
used only the local basename `trial-v1`, colliding with the completed pilot.
This happened before any GPU process swap. Both earlier initialization failures
and this refusal remain in the
[failed successor pack](platform480-2026-10-25/successor-v2-failed/queue-report.json).
The controller now hashes the entire absolute campaign path for configuration
identity, with a regression check for identical basenames under different parents.

The corrected, immutable `2ed95df` source snapshot completed independently on
the Pod under `/root/batchforge-runtime/platform480-20261025-v3`. Its
[actual report](platform480-2026-10-25/kv-v3/trial-v1/platform/report.json) and
[analysis](platform480-2026-10-25/kv-v3/analysis.json) are exported with the
[source/transfer hashes](platform480-2026-10-25/kv-v3/evidence-manifest.json).

It preregistered three ABBA repetitions of static8 versus exact-token32, with
60 mixed tasks per phase: 720 performance tasks. Both treatments retain fair
policy and the same baseline8 price projection. Additional admitted claims
cannot manufacture a 4× cost discount. Two further 60-task fault cohorts use
the adaptive worker, including a fresh physical-cache check after engine reload.
The report separately records failed/expired attempts, accepted usage, stale
heartbeat/completion fencing, API-restart readback and sampler gaps.

Each treatment completed 360 tasks in six measured bursts. The values below
pool durable task completion observations; throughput weights by phase wall
time, rather than averaging phase rates or percentiles.

| Admission | Output tokens/s | P50 s | P95 s | P99 s | Allocation wall h / million output tokens |
| --- | ---: | ---: | ---: | ---: | ---: |
| Static8, full contexts | 173.025 | 107.013 | 205.480 | 234.285 | 1.6054 |
| Exact-token32, bounded KV | 324.597 | 45.610 | 111.232 | 122.619 | 0.8558 |

The observed throughput ratio is **1.876×**; P95 is 45.87% lower and P99 is
47.66% lower. Individual ABBA block ratios were **1.874×, 1.980×, 1.779×**.
Allocation wall time per output token fell 46.70% within measurement windows.
This excludes model loading, inter-phase setup and fault recovery. It is not a
measured bill reduction: the existing Pod remained allocated and its current
hourly price is unknown.

This removes queueing, not GPU kernel time. Median queue time fell from 85.299 s
to 2.812 s. More concurrent work increased accepted-attempt service time: for
example, decode-heavy mean service time rose from 48.570 s to 66.152 s, while
its mean creation-to-completion latency fell from 126.985 s to 76.874 s.
These are distinct measurements; a shorter queue does not imply that each
individual generation runs faster.

Within the same mixed-arrival bursts, the requested prefill-heavy cells
(8K/16K input, 32/128 output) had P95 **184.249 → 65.522 s**. Decode-heavy
cells (128/512 input, 512/2K output) had P95 **223.437 → 117.636 s**. Each of
these class/treatment samples has 72 tasks. They are stratified observations,
not separate isolated workload-class trials or quality evaluations. The three
ABBA blocks and correlated requests do not establish a long-term P99 SLA or
statistical significance across independent deployments.

Recorded NVML arithmetic mean utilization for GPU0/1/2/3 was
**91.19/58.25/92.64/93.20%** under static8 and
**88.09/71.45/89.96/90.06%** under exact-token32. All four devices participate
in TP4; the model's tokens/s cannot be attributed as independent per-card
throughput. The sampled maximum real engine concurrency reached 32, versus 8
in every static phase. Reservation peaks never exceeded 164,256 tokens, no
admission pause was observed, and engine preemption counters stayed zero in
the performance windows. These windows had no sampling interval over 5 s.
This is not continuous 100% utilization or achieved FLOPs. The
[topology snapshot](platform480-2026-10-25/kv-v3/hardware-topology.json) shows
NV18 between all GPU pairs; it is not a measured link-bandwidth result. Host
CPU affinity is recorded, but the attempted cgroup-v2 quota paths were absent;
no available-vCPU quota is inferred from that affinity.

The two 60-task adaptive fault cohorts captured 32 valid leases each. Worker
loss recovered service in **20.142 s**, with all cohort tasks accepted after
**139.347 s**. Engine+worker loss recovered service in **72.875 s**, with the
cohort accepted after **193.702 s**. Both stale heartbeat and stale completion
were fenced with 409. All **840/840** tasks passed conserved accepted usage;
14 S3 input objects and 14 output archives passed 28 file readbacks after the
canary API restart. At that observation 780 response payloads were already
archive-only and 60 remained in Azure; task identities and usage remained in
Azure throughout. The parent restored 235B/worker/watchdog at 11:43:37 UTC with
[`restore_failures: []`](platform480-2026-10-25/kv-v3/trial-v1/trial.json).

## Primary serving promotion and real public-API validation

The [promotion](../../ops/promote480.py) requires a closed successful three-block
study, both adaptive fault scopes, all restart readbacks and prior restoration.
It rehashed **252,341,633,360 actual checkpoint bytes**, preserving the original
51-shard receipt. Both primary API replicas demonstrably rejected new batches
before the drained GPU swap; historical reads remained available. The new
worker's exact-model tokenizer/quiescence checks and the watchdog were ready
before admission reopened. Old configs and the 235B serving manifest remain
private on the Pod for bounded rollback. Newly accepted 480B work must drain
before rollback is allowed to stop its runtime.

Primary catalog activation completed **2026-10-25 11:50:51 UTC / 15:50:51 Dubai**.
The original primary lease policy was 90 s, whereas the qualification used
15 s. A separate admission-close/drain/worker-registration operation aligned
both APIs to the tested **15-second lease**, completing at 12:00:44 UTC. That
[alignment receipt](platform480-2026-10-25/primary-v2/lease-alignment.json) is
retained separately; the original promotion report was not rewritten. Future
promotions explicitly carry the tested lease policy as well as fair scheduling.

The serving state is now:

  is advertised for new work. All historical model results remain readable.

  exact-token32 with budget 164,256; existing primary watchdog active.
- Existing Azure database and existing S3 endpoint; no new endpoint, cloud
  resource, GPU, plan, schema or paid inference API.

The [primary validation](../../ops/validate_primary480.py) then submitted 20
ordinary real tasks through **gateway 8080**. It completed **20/20**, with
exactly one accepted attempt per task by the promoted worker and conserved
109,056 prompt / 13,600 completion tokens. All six sampled input/output files

[actual benchmark](platform480-2026-10-25/primary-v2/primary-smoke.json),

This final burst is a functional serving check, not an additional controlled
performance comparison. The completed campaign total is **1,060 real Batch API
tasks**: 200 pilot + 840 KV/recovery + 20 primary validation.

External persistence is distinct from unlimited retention. The existing input
retention policy remains 24 hours, input GC remains enabled, and result archival
starts after 120 seconds for its existing configured time range. This rollout
does not introduce an indefinite-retention promise or change those policies.
Checkpoint staging and live local logs still cannot survive whole-Pod loss;
exported evidence, Azure ledgers and ready S3 objects have separate durability.
Related focused verification: **57 passed**; real GPU evidence is recorded
separately above rather than being represented by those local tests.

Worker process loss and engine+worker process loss on this Pod are application
recovery experiments. They are not independent-node failover or production HA.
No measured result here establishes ten million tasks/day.
