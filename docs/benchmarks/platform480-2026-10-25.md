# 480B through the durable Batch API on the existing four H100s

This follows the [engine qualification](gpu-takeover-2026-10-25.md). The pinned
model is `QuantTrio/Qwen3-Coder-480B-A35B-Instruct-AWQ`, revision
`9ce3eaa67fe88609afec235117e97eb03d9b3cda`: 480B total / approximately 35B
active MoE parameters. No additional cloud resource or paid plan was created.
The current GPU invoice is unknown; measured monetary cost remains `null`.

## Execution and acceptance boundary

The finite canary uses the existing Azure PostgreSQL database and existing S3
HTTPS endpoint. It sends ordinary authenticated `POST /v1/files` and
`POST /v1/batches`, polls the Batch API, and downloads and validates real result
files. Its model-specific worker invokes the real TP4 vLLM engine. This is not
the fixture inference adapter or a direct-engine benchmark.

Canary API/worker ports are private 18148/9118; the engine port is 8348. The
primary API/gateway remain present, while their 235B worker/engine are stopped
during the GPU experiment. Success and failure both enter a bounded restoration
of the original serving pair and watchdog. An experimental canary is distinct
from promoting 480B into the primary serving catalog.

Every completed cohort must satisfy all of these invariants:

- Exactly one accepted completed attempt for each completed task.
- Identical accepted token totals in batches, tasks and attempts.
- All requested custom IDs occur exactly once in the downloaded results.
- Actual prompt/output counts equal the preregistered token-cell workload.
- Queue, accepted-attempt and durable completion timestamps come from Azure.

Inputs use the existing pinned public SQuAD text, fitted to 128/512/2,048/8,192/
16,384 tokens, crossed with output caps of 32/128/512/2,048. `min_tokens` fixes
the generated work for capacity comparison. These experiments do not grade
answer quality. Twenty tasks mean 109,056 input and 13,600 output tokens.

## Completed pilot, including persistence and fault qualification

All eight performance phases completed, 160/160 tasks, with conserved durable
usage. Each study has one ABBA block. Throughput below is total accepted output
tokens divided by total measured phase wall time. Latencies pool the 40 task
observations in each treatment, measured from durable creation to acceptance.
They are descriptive values from correlated bursts, not stable P99 SLAs.
The two fault cohorts add 40 tasks: the complete pilot accepted **200/200**,
1,090,560 prompt tokens and 136,000 completion tokens.

## Storage and durability

The primary API uploaded a 260-byte fixture to the existing S3 backend and
read back the identical SHA-256
`6457519d053fb91aca9701fb167b5660179921fea372d329c65786b6875f7738`.
The experiment subsequently requires all its inputs to be external ready S3
objects, explicitly archives its own completed outputs with immutable hashes,
restarts its API and verifies every input/output file digest again. The experiment
itself requested archive-only qualification. The original report incorrectly
asserted `database_payloads_retained: true` without observing other APIs'
background publishers. A subsequent read-only Azure audit found that the existing
primary publishers had already moved all 200 fixture responses/bodies to their
ten ready S3 archives; task identities and usage remain in Azure. The
[correction](platform480-2026-10-25/pilot-v1/storage-audit-correction.json) binds
the original report by SHA-256 and records actual counts. The original report
was not rewritten. Future reports query retained payload counts directly.
The 20 input/output SHA-256 readbacks passed after the canary API restart.

`/workspace` still fails with ENOMEM and remains excluded from mutable runtime
state. This addresses the application path through direct object storage; it
does not claim to repair the provider's FUSE mount. Logs, model staging and
journals use the existing container disk, which is not whole-Pod-loss durable.
The 252 GB checkpoint has pinned public source hashes but no newly uploaded
off-Pod checkpoint copy. Closed evidence is exported to the Mac and private Git
with a size-bounded allowlist and verified transfer hashes.

## Preregistered KV experiment now running

The qualified engine has 172,912 physical KV tokens and 32 maximum sequences.
Eight block-rounded full contexts reserve 147,584 tokens. Sixteen full contexts
do not safely fit. The new operator-only adaptive mode obtains exact prompt
tokens from this exact model's vLLM tokenizer and reserves prompt plus maximum
output in 16-token blocks. Its 164,256-token budget preserves a 5% physical
margin. HTTP/model/usage uncertainty latches admissions closed; engine health
alone cannot reset that latch. Waiting claimed tasks retain lease heartbeats.

The first successor verified pilot restoration, all managed identities,
a drained global queue and exact worker-source hashes before deploying two
compatible worker modules. Its trial refused to proceed: configuration names
used only the local basename `trial-v1`, colliding with the completed pilot.
This happened before any GPU process swap. Both earlier initialization failures
and this refusal remain in the
[failed successor pack](platform480-2026-10-25/successor-v2-failed/queue-report.json).
The controller now hashes the entire absolute campaign path for configuration
identity, with a regression check for identical basenames under different parents.

The corrected, immutable `2ed95df` source snapshot is running independently on
the Pod under `/root/batchforge-runtime/platform480-20261025-v3`. Its reports
remain in progress; no optimized KV throughput result is claimed yet.

It preregisters three ABBA repetitions of static8 versus exact-token32, with
60 mixed tasks per phase: 720 performance tasks. Both treatments retain fair
policy and the same baseline8 price projection. Additional admitted claims
cannot manufacture a 4× cost discount. Two further 60-task fault cohorts use
the adaptive worker, including a fresh physical-cache check after engine reload.
The report separately records failed/expired attempts, accepted usage, stale
heartbeat/completion fencing, API-restart readback and sampler gaps.

Worker process loss and engine+worker process loss on this Pod are application
recovery experiments. They are not independent-node failover or production HA.
No measured result here establishes ten million tasks/day.
